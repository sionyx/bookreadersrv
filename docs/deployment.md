# Деплой бэкенда

Обычный запрос «сделай деплой» означает следующий процесс. Дополнительного
уточнения способа сборки не требуется. Документ относится к бэкенду;
у сайта и MCP отдельные проекты и процессы выпуска.

## Адреса и конфигурация

- Репозиторий: `git@github.com:sionyx/bookreadersrv.git`, ветка `main`.
- Сборка: `.github/workflows/build.yml`, GitHub Actions **Build and Push Docker Image**.
- Образ: `ghcr.io/sionyx/bookreadersrv:main`, Linux amd64.
- SSH: `ssh ubuntu@217.16.23.85` (сверить актуальный адрес в
  `../../PROJECT_OVERVIEW.md`, раздел «Сервер и админка»).
- Рабочий каталог сервера: `/home/ubuntu/bookreadersrv`.
- Compose-проект: `bookreadersrv`; сервисы `app`, `db`, `migrate`, `revert`.
- Основной конфиг: `docker-compose.yml`; наложение с образом и S3:
  `docker-compose.override.yml` (на сервере это JSON, совместимый с YAML).
- Контейнер API: `bookreadersrv-app-1`; PostgreSQL: `bookreadersrv-db-1`.
- Сеть: `bookreadersrv_default`; API на хосте: `http://127.0.0.1:8080`.
- `Resources` монтируются с сервера в `/app/Resources`: изменения шаблонов
  нужно доставлять отдельно, один новый образ не обновляет этот том.
- Секреты остаются в серверном `.env`; не выводить их в логи и не копировать
  локальную конфигурацию поверх серверной. Резервные копии конфигов/БД —
  каталог 0700, файлы 0600 в `/home/ubuntu/bookreader-deployments/<release>/`.

## Подготовка и сборка

1. Проверить `git status`, diff, текущую ветку и `origin/main` после fetch.
   Коммитить только относящиеся к релизу файлы. Запрос деплоя разрешает
   коммит и push необходимых изменений. Amend и переписывание истории —
   только по отдельному запросу. Посторонние локальные правки не включать.
2. Проверить сборку Swift и согласованность OpenAPI. Проверки должны
   соответствовать изменениям; не добавлять тесты, если пользователь запретил.
3. Сделать обычный commit/push в `main`. Push запускает сборку в Actions.
   Дождаться `completed/success` именно для SHA отправленного коммита;
   один факт запуска workflow не подтверждает сборку.
4. На сервере проверить контейнеры, конфигурацию и свободное место.
   При нехватке места допустимо убрать ненужный build cache; не удалять
   тома БД, registry, образы отката и чужие контейнеры.
5. Выполнить `docker pull ghcr.io/sionyx/bookreadersrv:main`. Проверить
   `org.opencontainers.image.revision` через `docker image inspect`:
   он должен совпасть с ожидаемым полным SHA. Сохранить `RepoDigests[0]`.
   Не разворачивать непроверенный плавающий тег.

## Бэкап, проверка миграций и переключение

Все команды Compose выполняются из рабочего каталога на сервере.

1. Сохранить текущий ID образа app под отдельным rollback-тегом, оба Compose
   файла и изменяемые шаблоны. Создать дамп PostgreSQL через `pg_dump`.
   Не выводить дамп или переменные окружения в ответ пользователю.
2. Для изменения схемы создать отдельную временную БД на основе дампа
   (`createdb`, `pg_restore`). Выполнить миграции новым образом с переопределённым
   `DATABASE_NAME`, запустить временный app без опубликованных портов и без
   сетевого алиаса основного app. Проверить новые API и сохранность данных.
   Тестовые изменения допускаются только в копии. Удалить временный app и БД.
3. Перед основной миграцией остановить только `app`, чтобы исключить запись
   старым кодом; сделать свежий дамп. В override заменить только `image`
   сервисов `app`, `migrate`, `revert` на проверенный `image@sha256:...`.
   Сохранить настройки БД/S3/сети/томов. Не заменять серверный Compose
   локальным: их назначения и значения различаются.
4. Выполнить `docker compose run --rm --no-deps migrate` новым образом.
   При отсутствии новых миграций этот шаг не меняет схему.
5. Обновить только изменённые файлы `Resources` с предварительным бэкапом,
   сохранив доступ контейнера к ним. Не удалять пользовательские шаблоны.
6. Запустить `docker compose up -d --no-deps --pull never app`.
   `docker compose down`, пересоздание db и перезапуск остальных сервисов
   для обычного релиза не нужны.

## Проверка после запуска

- Подтвердить SHA образа запущенного app и успешный запуск.
- Проверить API локально и через HTTPS: `https://20min.fun/api/books`,
  `https://vsluh.app/api/sections`; проверить новый функционал релиза.
- Проверить `https://vsluh.app` и `https://manage.20min.fun/sections`.
- Для link_name: UUID и link_name должны возвращать одну запись; проверить
  списки/поиск/метаданные, книги автора (включая соавторов), вложенных авторов
  книги, содержимое/путь раздела и серверные страницы.
- Для медиа: временный уникальный объект допустим только в назначенном
  бакете; проверить public-read чтением без подписи и удалить объект.
  Не менять ACL существующих объектов без отдельного запроса.
- Записать SHA, digest, результат миграций и каталог бэкапа в итог релиза.

## Откат

Для релиза без несовместимой миграции восстановить прежний override и
изменённые Resources, затем пересоздать только app с прежним образом.

При несовместимой схеме одного возврата образа недостаточно. Остановить app,
сверить применённые миграции и выполнить revert именно новой партии новым
образом, либо согласованное восстановление дампа. `revert` откатывает партию,
а не произвольную одну миграцию. После восстановления схемы вернуть старые
Resources/override и запустить старый app. Проверить доступность API.

Если после выпуска уже были пользовательские записи, восстановление дампа
может потерять их: не делать это автоматически. Не запускать старый код с
несовместимой схемой и не объявлять откат успешным без проверки API.
